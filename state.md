## Working Features

### Frontend (`app/page.tsx`)
- Dark-theme UI ("Clinical Copilot") with a two-column layout
- Left column: PDF upload + manual form entry (both feed the same pipeline)
- Right column: analysis results panel
- HITL override panel: renders when `status === "pending_human_review"`, requires physician to type a justification (min 10 chars) before the approve button activates
- NextAuth session state shown in header (Physician Login / Sign Out)
- `resume_url` is intentionally commented out of all frontend state — the client never sees or stores it

### API Routes

| Route | Method | What it does |
|---|---|---|
| `/api/triage` | POST | Validates patient data, generates `session_id` server-side via `crypto.randomUUID()`, fires n8n webhook |
| `/api/upload` | POST | Accepts PDF via multipart form, parses with `pdf2json` server-side, returns raw text |
| `/api/override` | POST | Auth-gated (NextAuth). Fetches `resume_url` from DB, runs Prisma transaction (status update + audit log + token nulling), then POSTs to n8n to thaw pipeline |
| `/api/auth/[...nextauth]` | GET/POST | NextAuth credential provider handler |

### Security Architecture (HITL)
- `resume_url` (n8n Wait node token) is stored in `triage_sessions` table, never returned to the frontend
- `/api/override` fetches it directly from DB using `session_id`
- Prisma transaction atomically: sets status → `approved_by_doctor`, writes immutable audit log, nulls the token
- Optimistic concurrency guard: `updateMany` with `where: { status: 'processing' }` — throws `RACE_CONDITION` error if another physician already approved (returns 409 to client)
- `physician_id` sourced exclusively from server-side NextAuth session, never from client payload

### Auth (`lib/authOptions.ts`)
- NextAuth CredentialsProvider with hardcoded prototype credential: `dr_house` / `medconflict123`
- JWT session strategy; `id` field (`dr_house_8991`) propagated into session via callbacks
- Prototype-only — not production auth

### Components
- `DocumentUpload.tsx` — PDF upload UI, calls `/api/upload` then `/api/triage`
- `TriageForm.tsx` — Manual patient intake form, calls `/api/triage` directly
- `AuthProvider.tsx` — NextAuth SessionProvider wrapper for `app/layout.tsx`

### Database (`prisma/schema.prisma`)
Prisma client pointed at Supabase PostgreSQL. Key models:

| Model | Notes |
|---|---|
| `triage_sessions` | Core session record. Has `resume_url` field for HITL token. RLS enabled. |
| `clinical_alerts` | Alerts generated by n8n pipeline per session. RLS enabled. |
| `audit_logs` | Immutable override log. Written inside Prisma transaction. RLS enabled. |
| `tenants` | Multi-tenant anchor. All core tables carry `tenant_id` FK. |
| `clinic_guidelines` | pgvector embedding store for RAG (schema ready, not wired to UI yet). |

### Dependencies Added
- `next-auth` — physician authentication
- `pdf2json` — server-side PDF text extraction
- `@prisma/client` + `prisma` — DB ORM pointed at Supabase

## What Is NOT Implemented Yet

- Real authentication (provider login, role-based access, multi-physician)
- Tenant-switching UI
- `clinic_guidelines` RAG wired to the frontend
- Automated tests (unit or integration)
- CI/CD pipeline
- Production environment config (env vars, secrets management)
- n8n workflow is external — not in this repo

---

## Architecture Invariants (Do Not Break)

1. Next.js makes **no direct LLM calls** — all AI processing is in n8n
2. `resume_url` is **never returned to the frontend** under any circumstances
3. All override approvals must go through `/api/override`, never direct n8n calls from the client
4. `physician_id` must always come from the server-side session, never client payload
5. The DB schema is multi-tenant but the UI is single-tenant prototype — do not conflate the two
